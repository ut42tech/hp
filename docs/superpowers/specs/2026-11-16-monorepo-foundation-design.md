# ut42tech monorepo 土台 設計書

- 日付: 2026-11-16
- 対象: `github.com/ut42tech/hp`（現在は空のリポジトリ）
- 範囲: monorepo の土台と `apps/web`（ut42tech.com）の雛形まで。ポートフォリオのデザインと中身は別の設計で扱う。

## 1. 目的と背景

ut42tech.com（Takuya Uehara のポートフォリオ）をリニューアルする。理由は3つある。

1. **デザインへの不満**。作り直すなら、この機会に構成も見直したい。
2. **技術スタックへの違和感**。現行サイトは Next.js（Vercel 上）で作られているが、中身はほぼ静的サイトであり、Next.js は重すぎると感じている。
3. **今後の拡張**。ブログ（`blog.ut42tech.com`）、デジタル名刺（Prairie Card のように、SNS へのリンクや QR コードをすぐ出せるもの）、エンジニアとしての遊び心を出したページ、将来の API やマイクロサービスなどを、サブドメインに分けて同じリポジトリで開発したい。アプリごとにフレームワークを選びつつ、アセットは使い回したい。

本設計書の目的は、こうした今後のアプリを無理なく足していける土台を作ることにある。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール

- pnpm workspaces と Vite+ による monorepo が動いている。
- 共有パッケージ（`tokens` / `assets` / `profile` / `config`）が存在し、`apps/web` から使われている。
- `apps/web`（Astro 7 + Vue + Tailwind v4）の雛形が、Vercel のプレビュー環境にデプロイできている。
- リポジトリのルートから、lint・format・型チェック・ビルドを一括で実行できる。CI でも同じものが走る。
- 新しいアプリ（Astro、Nuxt、Vite + Vue、Next.js、Hono など）を `apps/` に足すときの手順が、README で分かる。

### 非ゴール（今回はやらない）

- ポートフォリオの実際のデザインやコンテンツ。雛形はプレースホルダーでよい。
- `apps/blog`、`apps/card`、`apps/api` の実装。
- 本番ドメイン `ut42tech.com` の切り替え。
- データベース、認証、CMS。
- 多言語対応の仕組み。現行サイトは日英を併記しているが、方針はデザインの設計で決める。

### アンチゴール（動いても失敗とみなすもの）

- **現行の ut42tech.com が壊れる、または止まる**。ドメインの付け替えは、新サイトが完成してから本人の承認を得て行う。
- 共有パッケージが特定の UI フレームワークに依存してしまい、ほかのフレームワークのアプリから使えなくなる。
- 共有パッケージが DOM や Vite 専用の機能に依存してしまい、将来のバックエンド（Hono）から import できなくなる。
- 土台が重くなりすぎて、アプリを1つ足すのに設定ファイルを何枚も書く必要がある。

## 3. 制約

- ホスティングは **Vercel**。現行サイトも Vercel 上で動いている。
- DNS は **Cloudflare** で管理しており、今後もそこに置いたままにする。
- 各サブドメインは、それぞれ独立した Vercel プロジェクトにする。
- 個人プロジェクトなので、Vercel の Hobby プランの範囲で運用できることが望ましい。
- **現行サイトの状況（2026-11-16 確認済み）**: Vercel のチーム `takuya-ueharas-projects`（Personal / Hobby）にあるプロジェクト `hp` が ut42tech.com を配信している。Git 連携の接続先は `ut42tech/hp-v1`（public archive）で、本リポジトリ `ut42tech/hp` にはつながっていない。したがって、本リポジトリへの push が現行サイトに影響することはない。
- **プロジェクト名の方針（本人が決定）**: 既存のプロジェクト `hp` を `hp-v1` に改名し、新しいプロジェクトを `hp-v2` として作る。リポジトリ名（`hp-v1` / `hp`）と対応が取れて分かりやすい。

## 4. 検討した選択肢

### 4.1 共有の範囲

| 案    | 内容                                                                                            | 判断                                                                                                                         |
| ----- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| A     | UI の部品まで共有し、見た目を完全に揃える                                                       | 不採用。部品を共有するには全アプリで同じ UI フレームワークを使う必要があり、フレームワークを使い分けたいという目的とぶつかる |
| **B** | **デザイントークン・フォント・ロゴ・プロフィールデータだけを共有し、UI の部品は各アプリで作る** | **採用（本人が選択）**                                                                                                       |
| C     | 画像程度しか共有しない                                                                          | 不採用。名刺とポートフォリオでプロフィール情報を二重に管理することになる                                                     |

### 4.2 デプロイ先

| 案                                | 長所                                                                                                 | 短所                                                      | 判断                   |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ---------------------- |
| Cloudflare Workers + 静的アセット | ドメインがすでにある。静的アセットへのリクエストが無料・無制限。Astro と Vite+ の開発元が Cloudflare | CD の使い心地は Vercel に劣る。Node.js 互換が完全ではない | 不採用                 |
| **Vercel**                        | **CD の使い心地が一番よい。Node.js がそのまま動き、将来の API やマイクロサービスにも対応しやすい**   | DNS は Cloudflare から CNAME で向ける必要がある           | **採用（本人が選択）** |

### 4.3 `apps/web` のフレームワーク

| 案                              | 判断                                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Astro 7 + Vue（アイランド）** | **採用**。State of JS 2025 のメタフレームワーク部門で満足度1位。標準では JS を送らず、静的サイトとの相性が一番よい。Vue と React のどちらの部品も使える |
| Nuxt（静的出力）                | 有力な対抗馬だが、ページ全体に Vue のランタイムが載る。アプリ寄りのもの（名刺、遊びのページ）向けに残しておく                                           |
| Next.js / React 系              | 不採用。現行サイトへの違和感をそのまま引き継いでしまう                                                                                                  |

選定基準は、本人の「今一番モダンで評価の高いものを使いたい」。

### 4.4 タスク実行とツールチェーン

| 案                | 判断                                                                                                                                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Vite+（`vp`）** | **採用（本人が選択）**。タスク実行・キャッシュ・Lint（Oxlint）・整形（Oxfmt）・テスト（Vitest）が一つにまとまる。2026年10月に 1.0                                                                                            |
| Turborepo         | 不採用。実績があり、Vercel のリモートキャッシュとも連携できるが、個人プロジェクトの規模ではその差を体感しにくい。タスクは各パッケージの `package.json` の scripts にあるので、後から `turbo.json` を足すだけで乗り換えられる |

Vite+ はまだリモートキャッシュを持っていない（ロードマップには入っている）。これは許容する。

## 6. 構成の詳細

```
hp/
├─ apps/
│  └─ web/                 ut42tech.com（Astro 7 + Vue）
├─ packages/
│  ├─ tokens/              デザイントークン
│  ├─ assets/              フォント・ロゴ・アイコン
│  ├─ profile/             プロフィールデータ
│  └─ config/              共通設定（tsconfig など）
├─ docs/superpowers/specs/ 設計書
├─ .github/workflows/      CI
├─ package.json            ルート（private、共通の scripts）
├─ pnpm-workspace.yaml
├─ vite.config.ts          Vite+ の設定（lint / fmt / タスク）
└─ .node-version           24
```

### 6.0 pnpm と Vite+ の役割分担

- **pnpm**: 実際に依存をインストールし、ワークスペースのパッケージ同士をリンクする。`pnpm-workspace.yaml` と `pnpm-lock.yaml` が正となる。
- **Vite+**: ルートの `packageManager` を読み、そのバージョンの pnpm を用意して呼び出す入口になる（`vp install` / `vp add` など）。手元で直接 `pnpm` を叩いても同じ結果になる。
- **Vercel**: `packageManager` と lockfile から pnpm を自動で検出して使う。Vite+ は使わない。

### 6.1 命名

- ワークスペースのパッケージ名は `@ut42tech/<name>` とする（例: `@ut42tech/tokens`）。すべて `private: true` で、npm には公開しない。
- 依存関係は `workspace:*` で参照する。
- **共有パッケージはビルドせず、TS / CSS のソースをそのまま `exports` で公開する**（設計者の判断）。各パッケージが持つタスクは型チェックとテストだけにする。利用する側（Astro / Vite / 将来の Hono のバンドラ）がソースを直接取り込む。こうすると共有パッケージを変えてもビルドの手間がなく、アプリに即座に反映される。将来、ビルドしないと動かない利用者が出てきたら、そのパッケージにだけ tsdown（Vite+ に同梱）を足す。

### 6.2 `packages/tokens`

- 役割: 色、タイポグラフィ、余白、角丸、影などのデザイントークン。
- 中身:
  - `tokens.css`: CSS カスタムプロパティを `:root` に定義する。ライトとダークの両方を持つ。ダークは `prefers-color-scheme` と `[data-theme="dark"]` の両方に対応する。
  - `theme.css`: Tailwind v4 の `@theme` で上の変数を参照し、Tailwind のユーティリティとして使えるようにする。
- Tailwind を使わないアプリでも、`tokens.css` を読み込むだけで使える。
- 値はプレースホルダーでよい。最終的な値はデザインの設計で決める。

### 6.3 `packages/assets`

- 役割: フォント、ロゴ（SVG）、ファビコン、SNS アイコンなど。
- `package.json` の `exports` でファイルを直接公開し、各アプリからは import（またはビルド時のコピー）で使う。
- ロゴやフォントの最終版はデザインの設計で決める。今回は置き場所と読み込み方を決めるところまで。

### 6.4 `packages/profile`

- 役割: 名前、肩書、所属、SNS リンクなど、本人に関するデータ。ポートフォリオ、名刺、ブログで共有する。
- **ランタイム依存のない素の TypeScript（ESM）**で書く。DOM、Vite、Astro、Vue に依存しない。将来 Hono からも import できるようにするため。
- 型（`Profile`、`SocialLink` など）とデータを export する。
- 初期データは現行サイトに載っている情報を元にしてよい。

### 6.5 `packages/config`

- 役割: 共通の `tsconfig`（`tsconfig.base.json` を各パッケージが `extends` する）。
- Lint と整形の設定は、ルートの `vite.config.ts`（Vite+）にまとめる。

### 6.6 `apps/web`

- Astro 7、`@astrojs/vue`、Tailwind v4（`@tailwindcss/vite`）。
- 出力は静的（`output: 'static'`）。サーバー機能が必要になったら `@astrojs/vercel` を足す。
- 雛形の中身:
  - トップページ1枚。`@ut42tech/profile` の名前と SNS リンクを表示し、`@ut42tech/tokens` の色とフォントが効いていることが分かるもの。
  - Vue のアイランドを1つ（ダーク / ライトの切り替えなど）。Vue の配線が動くことを確認するためのもの。
  - 基本の `<head>`（title、description、OGP の枠、favicon）。
- `package.json` の scripts は `dev` / `build` / `preview` / `check`（`astro check`）を持つ。

### 6.7 ルートのタスク

- ルートから次を実行できるようにする:
  - `dev`: 指定したアプリの開発サーバーを起動する
  - `build`: 全パッケージを依存順にビルドする
  - `check`: lint、format チェック、型チェックをまとめて実行する
  - `test`: Vitest（今回は共有パッケージの最小限のテストのみ）
- タスクの実行は `vp run` で行い、依存順の並べ替えとキャッシュを任せる。

### 6.8 デプロイ（Vercel）

- **Vercel プロジェクトの作成は Claude が行う**（本人が依頼済み）。作成先はチーム `takuya-ueharas-projects`。
- **既存プロジェクトの改名（`hp` → `hp-v1`）**:
  - 改名しても、本番ドメイン `ut42tech.com`、Git 連携、過去のデプロイには影響しない。変わるのは、プロジェクト名から自動で作られる `*.vercel.app` のエイリアスとダッシュボードの URL だけ。
  - 改名の前に、旧エイリアス（`hp-*.vercel.app` など）を外部から参照していないかを本人に確認する。
  - 改名は本番のプロジェクトに対する変更なので、実行する直前に本人の承認を取る。改名した後は、`ut42tech.com` がこれまで通り 200 を返すことを確認する。
- `apps/web` 用に、プロジェクト `hp-v2` を新しく作る。Root Directory は `apps/web`、Framework は Astro、Git 連携先は `ut42tech/hp`、本番ブランチは `main`。
- 「Include files outside the root directory」は有効のままにする（`packages/*` を参照するため）。
- 「Skip unaffected projects」（変更のないプロジェクトのビルドをスキップする機能）を有効にする。条件は次の3つで、本設計はすべて満たすようにする: pnpm workspaces を使うこと、すべてのパッケージに一意の `name` があること、パッケージ間の依存を各 `package.json` に明示すること。
- ルートの `package.json` に `packageManager`（pnpm のバージョン）を書いて、Vercel 上の pnpm のバージョンを固定する。
- Vercel 上のビルドは `apps/web` の `build` スクリプト（`astro build`）をそのまま使う。Vercel 側では `vp` を必要としない。
- この段階では `*.vercel.app` のプレビュー URL と本番 URL だけで運用する。**`ut42tech.com` は現行のプロジェクトに付けたままにしておく。**
- 将来サブドメインを足すときは、Vercel プロジェクトを1つ作り、Cloudflare に CNAME を1行足す（Vercel を使う場合、プロキシはオフにして DNS のみにする）。この手順を README に書いておく。

### 6.9 CI（GitHub Actions）

- PR と `main` への push で `check` と `build` を実行する。
- Vite+ の公式の setup アクション（`voidzero-dev/setup-vp`）を使う。Node のセットアップ、pnpm のセットアップ、`vp install`、キャッシュまでをまとめて行ってくれる。**バージョンは正確なリリース番号か commit SHA で固定する**（公式の指示。`v1` タグはもう更新されない）。
- デプロイは Vercel の Git 連携に任せ、CI では行わない。

### 6.10 調査で分かった、実装上の注意（2026-11 時点の公式ドキュメント）

- **Vite+ と Astro**: Astro は自分で Vite を起動し、`vite.config.ts` を読まない（`configFile: false`）。そのため、ルートの `vite.config.ts`（Vite+ の設定）が Astro のビルドに干渉することはない。一方、Vite+ は Astro のプロジェクトで `vp dev` と `vp build` の実行を拒否し、`vp run dev` を使うよう案内する。したがって、**Astro のアプリは package.json の scripts（`astro dev` / `astro build`）を `vp run` で呼ぶ**形にする。`apps/web` の中には `vite.config.ts` を置かない。
- **Lint と整形の設定**: ルートの `vite.config.ts` の `lint` と `fmt` に一本化する。パッケージごとの違いは `overrides` で書く。`.oxlintrc.json` などの個別の設定ファイルは使わない（公式の推奨）。
- **キャッシュ**: `vp run` では、`vite.config.ts` に定義したタスクはキャッシュされるが、`package.json` の scripts は**標準ではキャッシュされない**。完了の条件 3 を満たすため、ルートの設定で scripts のキャッシュを有効にする（`run.cache.scripts: true`）か、主要なタスクを `vite.config.ts` に定義する。どちらにするかは実装する人に任せる。
- **`.astro` と `.vue` の Lint**: Oxlint はスクリプト部分（Astro の frontmatter、Vue の `<script>`）だけを Lint し、テンプレート部分は Lint しない。型を見るルールも、今のところこれらのファイルでは動かない。**テンプレートの型チェックは `astro check`（`.astro`）と `vue-tsc`（`.vue`）で補う**。これを `check` タスクに含める。
- **`.astro` と `.vue` の整形**: Oxfmt は `.vue` をネイティブで整形できる。`.astro` は `fmt` の設定で `astro: true` を指定し、`@astrojs/compiler-rs` を devDependency に入れれば整形できる。Prettier は不要。
- **Tailwind v4 のトークン共有**: `packages/tokens` は CSS ファイルを `exports` で直接公開し、ビルドの手順は持たない。アプリ側の CSS では `@import "tailwindcss";` の後に `@import "@ut42tech/tokens/theme.css";` を書く。共有パッケージにクラス名を含むファイルを置いた場合に限り、アプリ側で `@source` を追加する（今回は部品を共有しないので不要）。

## 7. 完了の条件

1. クリーンな clone から `vp install`（または `pnpm install`）を実行し、ルートの `build` と `check` がエラーなく通る。
2. `apps/web` の開発サーバーで、トップページにプロフィールとトークンが反映され、Vue のアイランドが動く。
3. 何も変更せずに `build` と `check` をもう一度実行すると、`vp run` のキャッシュによってタスクがスキップされる。
4. `apps/web` が Vercel にデプロイされ、プレビュー URL で表示できる。
5. 現行の ut42tech.com に影響がない。
6. README に、全体の構成、各コマンド、アプリの追加手順、サブドメインの追加手順が書かれている。

## 8. 実装する人に任せること

- 各ツールの具体的なバージョン（その時点の最新の安定版を使う）。
- Vite+ の設定の書き方（`vite.config.ts` 内の lint / fmt / run の各設定）。公式ドキュメントを確認して決めること。
- `vp run` のキャッシュを有効にする方法（6.10 参照）。
- `assets` を各アプリに渡す具体的な方法（import か、ビルド時のコピーか）。
- トークンのプレースホルダーの値。
- テストの書き方と範囲（共有パッケージの型とデータが壊れていないことを確かめる程度でよい）。
