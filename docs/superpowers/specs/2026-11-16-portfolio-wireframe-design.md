# ポートフォリオ 構造（ワイヤーフレーム）設計書

- 日付: 2026-11-16
- 対象: `apps/web`（ut42tech.com）の画面構造と操作の流れ
- 範囲: スマホとパソコンのワイヤーフレームを Figma で作るところまで。色・書体・装飾などの見た目と、コードでの実装は別の設計で扱う。
- 置き換え: [`2026-11-16-portfolio-figma-design.md`](2026-11-16-portfolio-figma-design.md)（キャンバス案）を置き換える。

## 1. 目的と背景

ポートフォリオの一番の目的は**第一印象**。開いた人にまず楽しんでもらう。本人は HCI を重視しており、派手さではなく、**自然さと気持ちよさ**で技術力とデザインセンスを体感してもらいたい。

一度キャンバス案（デザインツールに見立てた画面と、カーソルが組み上げる演出）で見た目と動きから作り始めた。しかし、次の2つの理由でやめた。

- 構造が固まっていないまま見た目を作ってしまった。
- 中身の構成（名前・モットー・タグを最初に並べ、経歴や作品を一覧で積む形）が旧サイトに引きずられていた。

そこで、**構造をワイヤーフレームとして先に固める**。

見る人の多くはスマホで開く。そのため**モバイルファースト**で考える。ただし、ありきたりなスマホサイトではなく、他と違う個性を出す。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール

- スマホとパソコンそれぞれについて、全画面の構造と、画面間の移り変わり（どの操作で何がどう動くか）がワイヤーフレームで決まっている。
- 実装者がワイヤーフレームを見て、画面の部品、遷移、ジェスチャーの扱いを迷わず組める。

### 非ゴール（今回はやらない）

- 色・書体・アイコン・装飾などの見た目。ワイヤーフレームはグレースケールで作る。
- コードでの実装と、動きの細かい数値（時間・イージング）。
- 文章の確定。ただし構造の判断に必要な分は、旧サイトの素材から実際の題名を使ってよい。
- タブレット専用の画面。スマホとパソコンの間の幅の扱いは、実装の段階で決める。
- 英語版。

### アンチゴール（できても失敗とみなすもの）

- **旧サイトの焼き直しに見える**こと。旧サイトの素材は中身として使うが、構成と見せ方は持ち込まない。
- 開いた直後に**文字が多い**こと。第一印象はクリーンにする。
- **Safari のジェスチャーとぶつかる**こと。端からの戻る操作や、画面全体の引っ張りと競合して、意図しない動きが起きる。
- **OS の偽物**に見えること。メニューバーや偽のウィンドウ、Apple のロゴや部品の描き写しはしない。取り入れるのは作法まで。
- 演出のせいで**中身にたどり着けない**こと。

## 3. 設計原則（本人と合意済み）

本人が大切にしている「気持ちいい操作」の考え方を、全画面に通す。

1. **すぐ反応する**
   - 押した瞬間に見た目が変わる。
   - 動きの出だしを遅くしない（ease-in で始めず、ease-out かスプリングを使う）。
   - アニメーションの途中でも、次の操作を受け付ける。
2. **動きがつながっている**
   - 位置や形を途切れさせない（例: タブを押したボタンから、シートがつながってせり上がる）。
   - 指を離したときの速さを、その後の動きに引き継ぐ。
3. **意図に応える**
   - 動かした距離だけでなく、払った勢いで判断する。慣性で止まる位置を予測し、小さく払っても閉じたい意図が伝わるようにする。
4. **遊びを加える**
   - 1〜3 が整ったうえで、触って気づく程度の気持ちよさを足す。派手にはしない。

加えて、**プラットフォームの作法に合わせる**。

- スマホは iOS アプリ、パソコンは macOS アプリの作法に寄せる（Apple のデザインガイドライン、SwiftUI のアプリに近い手触り）。
- あくまで Web ページであり、OS を模倣した画面にはしない。

- **ハンドル `@ut42tech`** は、ナビゲーションの位置で小さく出す（Claude の提案）。本名「Takuya Uehara」は About の中だけで使う。
- あいさつ（例: 「hi.」）は 3D の上に小さく残す（Claude の提案）。
- **About / Works / Press** の3つを、ナビゲーションの入り口にする。Contact は About にまとめる（本人の決定）。

- **研究は紹介しない。** 個人としての自分と、研究者としての自分を分ける（本人の決定）。研究で作ったアプリは Apps に入れる。研究を紹介するページは、将来 `research.ut42tech.com` のような別のサブドメインで作るかもしれない。そこへの誘導（About からのリンク）はしてよい。ただし、研究のサイトが公開されるまではリンクを載せない（本人の決定、2026-11-17）。

中身の素材は、旧サイトの作品約10件、活動・役職5件、掲載1件、年表約30件を使う。

メールアドレスは `packages/profile` にまだ無い。実装の段階で `email` を足す（今回の範囲外）。

## 6. スマホの構造（幅 390 を基準）

### 6.1 画面と流れ（本人と合意済み）

1. **Hello**
   - 画面いっぱいに 3D のビジュアルを置く。指でドラッグして触れる。
   - 左上に小さく `@ut42tech`、3D の上に小さくあいさつ。
   - 下に浮いたタブバー（About / Works / Press）を置く。
2. **タブを押す**
   - ボタンが押した瞬間に沈み、シートが下からせり上がって**全画面**で開く（本人と合意）。シートの上端は上から 56px で、その上に Hello の 3D がわずかに覗く。
   - シートの中身は、シートの中だけでスクロールする。
3. **シートを閉じる**
   - 下に払うと閉じる。閉じるかどうかは、払った距離だけでなく勢いで判断する。
4. **Works の分類を切り替える**
   - シートの上部の切り替え（Apps / Career / Awards / Events。iOS のセグメンテッドコントロール）を押すと、その場で中身が入れ替わる。開いた直後は Apps（Claude の提案。パソコンの縦並びボタンを、スマホでは横一列の切り替えにする。階層を増やさず1タップで行き来できるため）。
   - カードは**2列**で小さめに並べる（本人の決定）。Career だけは横長カードの縦1列。
   - 切り替えの下に件数と並び替え（新しい順／古い順）。
5. **Apps の詳細**
   - カードを押すと、サムネイルがそのまま広がって詳細になる（シートの上に重なる全画面の層）。
6. **閉じる**
   - 詳細を下に払うと、画像が勢いのまま元のカードへ戻る。強く投げると画面の外へ飛ばせる（遊び）。
   - シートも下に払うと閉じる。

### 6.2 シートの高さの決まり（本人と合意済み）

原則: **裏にあるものに、まだ意味があるときだけ「半分」で開く。** それ以外は全画面。

| 状況 | 開き方 |
| --- | --- |
| Hello からタブで開く（MVP） | 全画面 |
| **詳細ページを開いているときに、別の場所のタブを押す** | **半分の高さで詳細の上に重ねる**。今は詳細ページが Apps だけだが、将来ほかの詳細ページが増えても同じ決まりにする |
| AI エージェントがページを開く（将来。10 章） | 半分（会話が見えたまま） |

詳細の上に重ねるときの制約（Claude の提案）:

- 重ねるのは**1枚まで**。重なったシートの中でさらにタブを押したら、もう1枚は積まず中身を入れ替える。
- 詳細と同じ場所のタブ（Apps の詳細を見ていて Works）を押したら、重ねずに詳細を閉じて一覧へ戻る。
- 重ねたシートを全画面まで広げたら、その場所へ移ったとみなし、裏の詳細は閉じる。
- 払う・戻る操作で閉じると、元の詳細に戻る。
- 裏の詳細は暗くするだけにする（ぼかしは端末によって重いため）。裏は操作できない状態（`inert`）にする。

### 6.3 シートとタブバーの関係（Claude の提案）

- **タブバーは常に見える**: シートや詳細が開いていても、浮いたタブバーは一番手前に残る。全画面のシートは、中身の最後がタブバーに隠れないよう下に余白をとる。
- **シートを開いたまま別のタブを押す**: シートを閉じずに、その場で中身だけが入れ替わる。
- **Works の切り替え**: カードの上に常に見える。

### 6.4 Apps の詳細（Claude の提案）

- 詳細は、シートの上に重なる全画面の層として開く。
- 詳細の中身がいちばん上までスクロールされているときだけ、下に払うと閉じる。途中までスクロールしているときは、下への操作は中身のスクロールになる。
- 画面の外へ飛ばす遊びは、上の画像の部分をつかんで強く投げたときだけ起こる。
- 端スワイプと戻るボタンでも閉じる（6.5 の 3）。

### 6.5 Safari と共存するためのルール（Claude の提案。本人の懸念から）

1. 横方向の操作は、画面の左右の端から始まらない位置にだけ置く。横スクロールはブラウザ標準のスクロール（CSS scroll-snap）で作り、独自のスワイプ処理は書かない。
2. シートを引き下ろす操作は、取っ手と見出しの部分だけで受ける。シート内のスクロールは外に伝えない（`overscroll-behavior: contain`）。裏の画面は動かさない。
3. シート、Works の分類、Apps の詳細はそれぞれ URL を持つ（例: `/works`、`/works/apps`、`/works/apps/<slug>`）。Safari の戻るボタンと端スワイプは、「詳細／シートを閉じる」として働く。詳細の上に重ねたシートは URL を変えず（裏の詳細の URL のまま）、履歴の状態だけで持つ。共有されたリンクを開くと詳細だけが開く。シートは `<dialog>` などブラウザ標準の重ね合わせの仕組みで作る。
4. タブバーは、画面下の安全領域と Safari の下部ツールバー（iOS 26 の浮いたタブバーを含む）に重ならない位置に置く。
5. 「視差効果を減らす」設定の人には、動きを控えめにする。
6. Hello の 3D は縦にスクロールしない1画面に置くので、ドラッグ操作はページのスクロールとぶつからない。画面の端から始まる操作は Safari の戻る操作を優先させる。「視差効果を減らす」設定の人や、3D が重い端末には、静止画か動画に切り替える。

## 7. パソコンの構造（幅 1440 を基準）

### 7.1 画面と流れ（本人と合意済み）

**全画面に共通すること**
- ブラウザの画面全体を1つのアプリとして使う。
- 上にツールバーを置く: 左に `@ut42tech`（Hello へ戻る）、中央に About / Works / Press の切り替え。

**画面ごと**
- **Hello**: ツールバーの下の領域いっぱいに 3D のビジュアルを置き、上に小さくあいさつ。
- **余白**（本人の指摘を受けて Claude が決めた値）: 中身の最大幅を **960px** にして、使える領域の中央に置く。Works ではサイドバー（280px）を除いた領域の中央、Press では画面の中央。About は読みやすさを優先して 720px の1列。
- **Works**: 左に Apps / Career / Awards / Events のボタンを縦に並べ、右に選んだ分類の中身を並べる（本人の決定）。Apps・Awards・Events は3列の共通カード、Career は 960px 幅の横長カードの縦1列（サムネイルは左）。右上に件数と並び替え。
- **Apps の詳細**: カードを押すと、右側がその場で詳細に切り替わる。左の分類ボタンは残る。`‹ Apps` か戻る操作で一覧へ（Claude の提案）。
- **About**: 読みやすい幅の1列で、ツールバーの下に表示する。
- **Press**: Apps と同じ共通カードを、同じ 960px 幅に3列で並べる。右上に並び替え。

### 7.2 補足（Claude の提案）

- **Works を選んだ直後**: Apps を選んだ状態で表示する。
- 切り替えの動き: 切り替えボタンを押すと、中身が入れ替わる。そのとき、ツールバーと `@ut42tech` は動かさない。
- URL はスマホと同じにする（`/about`、`/works/apps`、`/works/apps/<slug>`、`/press`）。

- **Hello を AI エージェントにする**: 本人のアバターとして、本人について何でも質問できる。答えるだけでなく、該当するページを引っ張ってくる・開くこともできる。
- **呼び出し方**: スマホはシートの裏（Hello）で会話する。パソコンは画面右下のボタンから呼ぶ。
- **エージェントが開くページは半分の高さ**（6.2）: 会話が見えたまま、結果を手前で確かめられる。
- **今のうちに押さえておくこと**（Claude の提案）:
  - スマホの Hello の下部（タブバーの上）に、将来の入力欄を置ける余白を残す。
  - パソコンの右下の呼び出しボタンが、Works や Press のカードに重ならないようにする（中身は最大幅 960px の中央寄せなので、右側に余白がある）。
  - Hello の 3D を、そのままエージェントの「顔」にする案を、3D の中身を決めるときの候補にする。
  - エージェントの答えはサイトの中身に基づかせ、根拠のページを開いて見せる形にする（誤った答えを抑えるため）。
